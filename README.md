# modular-agentic-system

**단계마다 갈아 끼울 수 있는 에이전트 파이프라인.**

공고를 읽고, 회사를 조사하고, 요구를 뽑고, 내 근거를 찾고, 문항별 소재를 정하고, 초안을 쓰고, 문장마다 근거를 대조한다. 이 흐름을 **업무와 실행 엔진에서 떼어 낸 뼈대**로 만들었다. 업무(자소서·제안서·포트폴리오)나 엔진(Strands·다른 프레임워크) 중 하나를 바꿔도 나머지는 그대로 돈다.

지금 구현된 업무는 자소서 작성 도우미다. 공고 한 건을 처음부터 초안까지 실제로 돌려 썼고, 만들면서 잰 실험은 모두 [기록](docs/experiments/)해 두었다.

> 개인 프로젝트(2026.09~). DevCraft 2026(AWS AgentCore 핸즈온) Build-up 기간에 시작했다.
> 5분이면 이 문서 → [`core/stages.py`](src/modular_agentic/core/stages.py)(단계 인터페이스) → [`docs/experiments/`](docs/experiments/) 순으로 보면 된다.

## 왜 만들었나

에이전트 파이프라인의 뼈대는 업무가 달라도 비슷하다. 입력을 읽고, 요구를 뽑고, 근거를 찾고, 결과물을 쓴다. 그런데 보통은 프레임워크와 업무가 한 덩어리로 엮여서, 두 번째 업무를 하려면 처음부터 다시 짠다.

그래서 뼈대와 업무와 엔진을 코드에서 나눴다. 두 번째 업무는 설정과 근거 자료만 바꿔 얹고, 엔진은 인터페이스만 맞추면 갈아 끼운다. 그리고 만드는 내내 "모델이 낸 것을 어디까지 믿을 수 있나"를 측정했다.

## 세 가지 비종속

- **기능 비종속.** 업무가 바뀌어도 파이프라인은 그대로다. `core/`는 업무를 모르고, 업무별 설정(근거 코퍼스, 제외 경로, 문항, 조사 주제)은 `instances/`에만 있다.
  - 확인: 자소서로 공고 → 조사 → 분석 → 매핑 → 소재 계획 → 초안 → 문장 검증을 한 건 끝까지 돌렸다.
  - 아직: **두 번째 업무(포트폴리오·제안서)는 돌려 보지 않았다.** 비종속은 설계이고 검증은 한 건이다.
- **기술 비종속.** 프레임워크가 바뀌어도 코어는 그대로다. 단계는 Protocol([`core/stages.py`](src/modular_agentic/core/stages.py))로 정의하고, 프레임워크는 `engines/strands/`에서만 쓴다. `pyproject.toml`의 기본 의존성은 비어 있다.
  - 확인: `core/`, `tools/`, `instances/`에 strands·boto3·langchain·anthropic import가 없다.
  - 아직: 엔진 구현은 Strands 하나다. 다른 엔진은 붙여 보지 않았다.
- **환경 비종속.** 서버·PC·클라우드 어디서든 같은 코드가 돈다. 모델·검색·경로는 설정으로 뺐다(`MAS_MODEL_ID`, `MAS_VAULT_DIR`). 검색은 환경에 따라 MCP → 상시 서버 → CLI 중 하나를 자동으로 고른다. 외부 명령은 `shell=True`나 cmd.exe 없이 직접 부른다.
  - 확인: Linux 서버와 Windows PC에서 실행했고, 단위 테스트 303개는 AWS·qmd 없이 통과한다.
  - 아직: 모델은 AWS Bedrock만, 검색은 qmd만 구현했다.

## 어떻게 생겼나

```
00 수집 ─▶ 01 조사 ─▶ 02 분석 ─▶ 03 매핑·검증 ─▶ 04 소재 계획 ─▶ 05 작성 ─▶ 문장 검증
 공고·자료   회사 조사     요구 목록     근거 찾기        문항별 소재       초안        문장마다
 이미지 전사  출처 인용     기본 요건     인용 대조        먼저 배정        피드백       근거 대조
              ▲ 사람이     ▲ 사람이                      ▲ 사람이                    ▲ 사람이
                승인         표시                          승인                        확인
```

단계마다 인터페이스, 구현, 결과 폴더, 사람이 확인하는 자리가 하나씩 있다.

| 단계 | 하는 일 | 결과 |
|---|---|---|
| 00 수집 | 공고(텍스트·이미지)와 회사 자료를 받는다. 긴 이미지는 조각내 전사한다 | `inputs/00_collect` |
| 01 조사 | **출처 인용이 붙은** 조사 보고서를 만든다. 인용이 자료에 없으면 코드가 그 주장을 버린다 | `logs/01_research` |
| 02 분석 | 공고에서 요구 목록을 뽑고, 사용자가 기본 요건을 표시한다 | `logs/02_analyze` |
| 03 매핑·검증 | 요구마다 근거를 검색해 확인·부분확인·TODO로 판정하고, 정정·과장이 없는지 검증한다 | `logs/03_map` |
| 04 소재 계획 | 문항마다 쓸 소재를 먼저 정해 같은 경험의 반복을 막는다 | `logs/04_plan` |
| 05 작성 | 승인된 계획대로 쓰고, 선택·피드백으로 작성 지침을 고친다 | `logs/05_write` |
| 문장 검증 | 문장마다 쓴 근거가 뒷받침하는지 판정한다. 사용자가 고친 글도 검사한다 | `*.check.md` |

분석 결과 문서는 이렇게 보인다(공고에서 뽑은 요구 일부).

```
3. [담당업무] AutoEver Code(사내 AI 코딩 플랫폼) 백엔드(Spring Boot/Java) 기능 개발·유지보수
5. [담당업무] AI 기능 연계(코드 생성·리뷰)
9. [필수] Java/Spring 백엔드 — 기본(어필 안 함)
```

세 가지 원칙을 지킨다.
1. **사람이 승인한 것만 다음 단계가 쓴다.** 조사 보고서와 소재 계획은 읽고 승인해야 넘어간다.
2. **모델이 낸 인용과 번호는 코드가 입력과 대조한다.** 모델은 그럴듯한 인용을 지어낼 수 있다.
3. **유사도 점수로 관련 여부를 판단하지 않는다.** 무관한 결과가 관련 결과와 같은 점수를 받는 것을 쟀다(실험 001).

## 실험

만들면서 쟀다. 모든 기록은 **가설 / 확인된 것 / 확인하지 못한 것**으로 나눠 쓰고, 결과를 본 뒤에 기준을 맞추지 않는다. 기각된 가설도 남긴다.

- **검색은 근거를 찾아 주는가** ([001](docs/experiments/001-vault-search-recall.md)). 개인 지식 베이스를 **qmd**(임베딩·키워드·리랭킹을 쓰는 로컬 하이브리드 검색, 이 레포 밖의 외부 도구)로 검색해 recall@k를 쟀다. 페이지 단위로 채점하면 recall@5가 **17%**인데 경험 단위로 채점하면 **57%**(@10 71%)다. 검색은 그대로이고 채점 기준만 바꿨다. "색인이 오래됐다"는 가설은 기각했다(활성 문서 245개 중 임베딩이 없는 것 0개). 문서 점수가 가장 비슷한 조각 하나로 정해져서 긴 문서가 유리할 수 있다는 것은 qmd 코드를 읽어 확인했다.
- **어디가 느린가** ([002](docs/experiments/002-strands-engine-first-run.md)). 시간을 단계별로 쪼개 호출마다 모델을 다시 올리는 고정 비용을 찾았고, qmd를 상시 서버로 바꿨다. 요구 5개 처리가 **292.6초 → 81.4초**, 검색이 차지하는 비율이 76% → 6%가 됐다. 병목은 검색에서 모델 응답으로 옮겨 갔다.
- **이미지 공고를 글로 옮길 수 있나** ([003](docs/experiments/003-image-posting-transcription.md)). 8000px 이미지를 한 번에 전사하면 단어가 바뀌고 **없는 전형 단계를 지어냈다.** 빈 줄에서 조각내 전사하니 대조한 범위에서 오류가 없었다. 인용 대조는 이 오류를 못 잡는다(잘못 옮긴 글이 "자료"가 되기 때문이다). 줄일 곳은 전사 단계였다.
- **문장 검증기는 믿을 만한가** ([004](docs/experiments/004-claim-checker-first-eval.md)). 사람이 라벨을 붙인 문장 27개로 쟀다. 근거에 없는 새 사실은 안정적으로 잡았지만, 근거에 관련 사실이 있는데 연결·동기를 덧붙인 문장은 불안정했다. **같은 입력에서 찾아낸 비율이 91%와 64%로 달라졌다.** 그래서 이 표시는 "확인할 문장 목록"으로만 쓴다. 평가 전에 프롬프트의 예시가 표본과 겹치는 것도 찾아 없앴다.

측정이 설계를 바꾼 곳도 있다.
- 소재 계획이 근거를 200자만 보고 골랐는데 작성은 400자까지 본다는 것을 코드 점검으로 찾아 고쳤다([설계 문서 23절](docs/design-research-stage.md)).
- 지시문에 쓴 수치가 인용 없이 초안에 들어가는 것을 찾아, 지시문에는 사실을 쓰지 않기로 했다.
- 요구에 조사 주장을 붙였더니 17개 중 11개가 공고를 다시 말하는 되풀이여서, 공고에서만 나온 주장은 코드로 빼고 이 맥락은 기본으로 쓰지 않게 했다(설계 문서 25절).

AWS AgentCore는 Runtime 안에서 Tailscale로 서버에 닿는 시험까지 했고([`docs/agentcore-research.md`](docs/agentcore-research.md)), 배포는 하지 않았다.

## 구성

| 위치 | 내용 |

| [`core/`](src/modular_agentic/core) | 타입, 단계 인터페이스, 사람이 확인하는 자리(조사 보고서·분석·소재 계획), 문장 검증과 인용 대조. **프레임워크를 모른다** |

| [`eval/`](src/modular_agentic/eval), [`scripts/`](scripts) | 평가 코드, 단계별 실행·실험 스크립트 |
| [`tests/`](tests), [`deploy/`](deploy) | 단위 테스트 303개, AgentCore 시험용 배포 코드 |

## 한계와 할 일

한계
- 도메인 비종속은 자소서 한 건으로만 검증했다.
- 엔진은 Strands, 모델은 Bedrock, 검색은 qmd 하나씩이다. 인터페이스로 나눴을 뿐 다른 구현을 붙여 본 것은 아니다.
- 자소서 업무는 개인 지식 베이스(마크다운)가 있어야 돈다. 그 내용은 개인 기록이라 공개하지 않아서, 전체 흐름을 그대로 재현할 수는 없고 테스트와 문서로 확인한다.
- 실험은 대부분 공고 한 건과 한 사람의 지식 베이스에서 나왔다. 표본이 작아서 비율은 방향을 보는 용도다.

할 일
- 두 번째 업무(포트폴리오 생성)로 같은 단계가 재사용되는지 확인한다.
- 문장 검증을 안정시킨다. 같은 글을 여러 번 검사해 합치는 방법을 새 공고의 새 초안으로 평가한다.
- 검색이 놓치는 소재를 위해 경험 목록(인벤토리)을 만든다.
- Strands 말고 다른 엔진을 하나 붙여 본다.
