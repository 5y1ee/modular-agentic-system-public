# 자소서 작성 규칙 (vault `CLAUDE.md`에서 옮김)

자소서 초안을 쓰거나 평가하는 세션과 Writer 프롬프트를 고칠 때 기준이 되는 규칙이다.

- **원본은 vault의 `CLAUDE.md`**(`~/01_user/knowledge-base/CLAUDE.md`의 "자소서 작성 규칙", "초안 vs 직접 수정"). 이 문서는 **2026-10-12 시점의 사본**이다. 한쪽을 고치면 다른 쪽도 같이 고친다.
- 사례 설명(Why)에 든 회사 이름은 공개용 복사본(`scripts/make_public_copy.py`) 때문에 "한 지원처"로 바꿨다. 규칙 문장은 원문 그대로다.
- 이 레포의 세션은 vault `CLAUDE.md`를 자동으로 읽지 못한다. 그래서 여기에 둔다.

## 자소서 작성 규칙 (vault: 2026-09-28 이관 · 09-30 4건 추가 · 10-12 1건 추가)

- 자소서 파일은 `06_career/자소서/20YY년 상반기|하반기/`에 둔다(파일명 `YY.MM-` 기준 1~6월 상반기, 7~12월 하반기). 새 자소서는 해당 폴더에 만들고, 위키링크는 파일 이름만 쓰므로 경로는 안 쓴다.
- 새 자소서 문항 초안은 요청 전에 처음부터 `[헤드라인]` 형태의 대괄호 소제목을 기본으로 넣는다(문항 → 빈 줄 → `[헤드라인]` → 빈 줄 → 본문). 단 헤드라인이 없는 자소서가 한 건 있으니 "이 볼트의 모든 자소서가 헤드라인을 쓴다"고 단정하지 말 것.
- 헤드라인 문구는 "~잘 아는/잘하는 개발자" 같은 자기평가형 표현을 피하고, "다루는/만드는/지키는" 같은 행동·역할 중심 동사로 끝내는 구조를 기본값으로 삼는다.
- 지원동기 문항은 회사 소개·채용공고 텍스트 재활용에 기대지 말고, 항상 웹서치로 "{회사명} 2026 AI/디지털전환/최근사업" 등을 검색해 최근 뉴스를 찾고, 지원자의 실제 경험과 시의성 있게 엮을 소재를 우선 채택한다. 소재가 없으면 그때 기존 방식으로 대체하되 검색 시도 자체는 기본 절차. 단 회사 소개 문구를 옮기지 말라는 뜻이지, 회사의 실제 제품·사업 구조와 내 경험의 접점을 직접 잇지 말라는 뜻이 아니다 — 그 연결이 지원동기·성장계획의 핵심이다. (Why 2026-09-30: 한 지원처 1번에서 그 회사 제품과 내 경험의 연결을 "소개 재활용"이라며 지웠다가 사용자가 되살림)
- 초안 전에 문항이 묻는 것과 공고(JD)의 요구를 먼저 해독해 (요구 / 내 근거 / 강도 / 다른 문항에서 쓴 여부) 대응표로 보여준 뒤 쓴다. 소재부터 고르지 않는다. (Why: 한 지원처 2번 "핵심 직무 역량"에 운영 트러블슈팅 한 면만 답해 "뭘 묻는 거냐"는 지적)
- 사용자가 준 재료를 다 넣지 않는다. 문항 논지를 강화하는 것만 고르고 약한 예시·사소한 디테일은 빼며, 사례는 보통 2개를 깊게 쓴다. 같은 에피소드가 과거 자소서에 있으면 새로 쓰기 전에 먼저 읽고 좋은 구조를 참고하되, **과거 서술을 정답으로 여겨 그대로 따르지는 않고** 지금 문항의 의도에 맞게 재구성한다. (Why: 한 지원처 3번을 과거 자소서 없이 써서 "더 구려졌다"는 지적, 반대로 과거 서술이 항상 최선은 아님 — 사용자 확인)
- 기술 인과(예: 생존 편향은 모델이 아니라 데이터 문제)는 사용자 설명대로 정확히 쓴다. 문장은 결론 먼저·짧게, 벤더 종속 표현(CLAUDE.md 등)·구어체·의미가 불분명한 추상 표현은 쓰지 않으며, 사용자가 직접 고친 판본이 기준 샘플이다. 자소서의 기술은 면접 질문이 되므로 사용자가 설명하기 어려워하는 사례는 빼거나 확인한다.
- (2026-10-12 추가, 현대오토에버 제출본과 파이프라인 초안을 비교해 도출) 처음 나오는 프로젝트명·데이터·내부 용어는 한 줄로 풀거나 일반어로 바꾼다(읽는 사람은 처음 보는 사람이다). 단 독자가 그 회사의 개발 직군이면 업계 표준 용어(스트리밍·파드·커넥션 풀·MCP 등)는 풀지 않고, 내 것이거나 덜 흔한 말(프로젝트명·사내 도구·멀티테넌트 등)만 푼다. (2026-10-12 지원처 13: 사용자가 최종본에서 스트리밍·파드·커넥션 풀·MCP 풀이를 지우고 멀티테넌트·qmd 풀이만 남김) 글쓰기 자체를 설명하는 문장("~을 쓰겠습니다", "확인된 범위는 위에 적은 것이 전부입니다")은 쓰지 않는다. 지원 판단·동기를 말하는 "~라고 판단해 지원했습니다" 같은 문장은 괜찮다. 긴 문단은 단계별 줄바꿈으로 나눈다. 지원동기·커리어 문항이면 첫 문단에 회사·직무 설명과 내 경험의 접점을 둔다. (Why: 사용자가 최종본에서 초안의 회사 연결을 뒤에서 앞으로 옮기고, 낯선 용어를 풀고, "자소서 티" 나는 메타 문장을 지우고, 긴 문단을 단계별로 나눔. 같은 네 줄이 `logs/guidance.md`에도 있다.)

## 초안 vs 직접 수정 — 소유권 원칙 (vault)

너(LLM)는 초안만 쓴다. 사용자가 직접 문장을 고칠 여지를 남기고, 채팅으로 고쳐 주기보다 직접 고치도록 기본으로 유도한다(채팅 수정은 차선책). 이미 있는 페이지를 고칠 때는 먼저 현재 내용을 다시 읽고, 사용자가 손댄 흔적이 보이면 덮어쓰지 말고 물어본다.

## MAS 코드에 반영된 정도 (2026-10-12, `engines/strands/writer.py` 프롬프트와 소재 계획 문서를 읽고 확인)

| 규칙 | 상태 |
|---|---|
| 근거에 없는 사실·내면·동기를 만들지 않기 | Writer 프롬프트에 있음(vault 규칙보다 더 자세함) |
| 대괄호 헤드라인, 행동·역할 중심 | Writer 프롬프트에 있음 |
| 결론 먼저·짧게, 구어체 금지 | Writer 프롬프트에 있음 |
| 재료를 다 넣지 않고 깊게(프롬프트는 2~3개, vault는 보통 2개) | 있음. 수치가 조금 다름 |
| 요구·근거·강도·다른 문항 사용 여부 대응표 | 소재 계획(Planner)이 구현 |
| 지원동기: 회사 조사로 최신 소재를 엮기 | 조사 단계(Researcher)와 "회사 사실"이 담당 |
| 이번 10-12 추가 네 줄 | `logs/guidance.md`(일반 지침). 이 기기에만 있음 |
| 벤더 종속 표현(CLAUDE.md 등) 금지 | Writer 프롬프트에서 못 찾음 |
| 프로덕션이 아닌 사고(dev/stg)를 프로덕션 장애로 쓰지 않기 (vault `CLAUDE.md`가 아니라 현대오토에버 자소서 파일의 "작성 규칙 요약"에 있음) | Writer 프롬프트에서 못 찾음 |
| 면접 질문이 될 사례는 설명 가능한지 사용자 확인 | Writer 프롬프트에서 못 찾음 |
| 과거 자소서는 구조만 참고하고 그대로 따르지 않기 | 검색에서 과거 자소서를 제외하는 방식으로 일부 대응. 프롬프트 규칙은 못 찾음 |
