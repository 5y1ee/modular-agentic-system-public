# 실험 004 — 문장 검증기가 근거에 없거나 부풀린 문장을 가려내는가

설계는 `docs/design-research-stage.md` 24절이다. 초안의 문장마다 쓴 근거가 뒷받침하는지 모델이 판정하고, 모델이 댄 인용이 근거에 있는지는 코드가 대조한다.
이 문서는 첫 평가를 기록한다. **결과가 나올 때마다 이어서 적는다.**

vault 상태: `b5d880e+cddef1f2(10)`(두 실행 모두 같음). 근거 발췌는 평가 때의 vault에서 읽었다.

## 1. 첫 평가 (2026-10-11)

### 가설
H1. 검증기는 사람이 근거와 대조해 틀리거나 근거 없다고 확인한 문장을 대부분 표시한다(찾아낸 비율).
H2. 근거에 있다고 확인한 문장은 거의 표시하지 않는다(오탐 비율).
판단 기준은 결과를 보기 전에 정하지 않았다(표본이 작아 방향만 본다). 아래 숫자는 결과를 본 뒤에 기준을 맞춘 것이 아니라 그대로 적은 것이다.

### 조건
- 모델: `us.anthropic.claude-sonnet-4-6`, temperature 0(`config.build_agent`). 검증기 프롬프트 해시 `55915bb5`. 두 실행의 프롬프트·입력·표본이 같다.
- 표본: `inputs/eval/claim_check_golden.json`(자소서 본문이 있어 git 제외). 사례 4개(현대오토에버 초안 3개 + 과거 자소서 혼합본 1개), 라벨 27개.
  - flag 11개: 사람이 근거와 대조해 찾은 틀린 문장 8개, 근거에 없는 수치·배포를 일부러 끼운 문장 3개(대조군)
  - pass 16개: 핵심 구절이 근거 원문에 있다고 확인한 문장
  - 라벨이 근거와 어긋나서 평가에서 뺀 것: 0개(평가 전에 모델 없이 점검했다)
- 검증기가 본 근거는 초안이 쓴 근거만이다. 발췌가 400자에서 잘린 곳이 표본 근거 24곳 중 16곳이다(검증기가 뒤쪽을 보지 못한다).
- 실행: `scripts/eval_claim_checker.py`를 같은 조건으로 2번. 보고서 `logs/reports/claim-check-eval-20261011.md`, `…-run2.md`(git 제외).

### 평가 전에 한 일: 표본 오염 제거
검증기 프롬프트를 이번 오류들을 본 뒤에 썼다. 첫 평가 전에 프롬프트를 점검하니 예시가 표본과 겹쳤다("시험했다 → 풀었다", "이 판단을 뒷받침했다"는 표본 라벨의 구절 그대로, "참여했다 → 체계적으로 정리했다", "저에게 맞는 환경", "한 프로젝트의 결과를 다른 프로젝트가 받쳤다"도 이번 오류에서 가져옴). 이를 표본과 무관한 일반 예시로 바꾸고 평가했다. 그래도 **어떤 종류의 오류를 잡을지(범위 확대, 인과·동기, 서로 다른 대상의 연결) 정한 것 자체가 이 표본에서 나왔다.** 그래서 이 숫자는 개발 표본 위의 값이다. 평가 뒤에는 이 표본에 맞춰 프롬프트를 고치지 않았다.

### 결과
| | 실행 1 | 실행 2 |
|---|---|---|
| 찾아낸 비율(flag 11개 중) | **10/11 = 91%** | **7/11 = 64%** |
| 그중 실제 초안에서 찾은 틀린 문장(8개) | 7/8 | 4/8 |
| 그중 심은 문장(3개) | 3/3 | 3/3 |
| 오탐(pass 16개 중 표시) | 2/16 = 12% | 2/16 = 12% |
| 라벨 없는 문장 36개 중 표시 | 12개 | 20개 |

**같은 입력·같은 프롬프트로 두 번 돌렸는데 27개 라벨 중 5개의 판정이 달라졌다.** 찾아낸 비율이 91%에서 64%로 바뀐 것은 이 때문이다.

flag 라벨별로 보면 이렇다.
- **두 번 다 표시**(7개): 심은 3개, 고객사 협업 문장(사용자 진술 없이 쓴 것), 12.6초(지시문에서 온 수치), 트러블슈팅(다른 제품 기능), "세 계층으로 분리"(AWS 구성을 본인 설계로).
- **한 번만 표시**(3개): "MCP 브리지 구조로 풀었고"(구현 미착수), 베타리더 동기("이 역량을 계속 갈고닦기 위해"), "개발 중심 문화가 이 판단을 뒷받침했다"(동기).
- **두 번 다 놓침**(1개): "이 프로젝트로 개인부문 우수상"(수상이 FINT 때문인지 근거에 없다). 근거에 수상 사실이 있어서 "뒷받침됨"으로 판정했다.

오탐 2개는 실행마다 달랐다. 두 번 다 나온 것은 "LightGBM으로 일일 수익률을 예측한 뒤…" 문장으로, 검증기가 댄 인용이 근거 원문에 없다고 **코드가 내린** 경우다(원인은 확인하지 못했다. 인용 대조가 지나치게 엄격한지, 검증기가 근거를 정확히 옮기지 못한 것인지 구분하지 못했고 인용 원문을 저장하지 않았다). 나머지 하나는 실행 1에서 사용자 진술이 근거인 포부 문장을 "근거 없음"으로, 실행 2에서 "MAS의 네 단계"를 근거 간 표기 차이(분석·매핑·검증·작성)로 "일부만" 표시한 것이다.

### 확인된 것
- 근거에 없는 **새 사실**(수치, 없는 사건, 다른 제품의 기능, 사용자 진술에 없는 협업)은 두 번 다 안정적으로 표시했다(위 7개).
- 근거에 **관련 사실이 있는데 연결·범위·동기를 덧붙인 문장**("풀었다", "이 프로젝트로 받았다", "~ 위해 참여했다", "~가 이 판단을 뒷받침했다")은 불안정하거나 놓쳤다(3개 한 번, 1개 두 번 놓침). 이 종류가 이번에 사람이 찾은 오류 8개 중 4개였고 가려내기가 가장 중요한 쪽이다.
- 같은 프롬프트라도 실행마다 결과가 달라서 **한 번 돌린 숫자를 성능으로 쓸 수 없다.**
- 라벨 없는 문장을 표시한 것이 많다(실행 1에서 12개, 실행 2에서 20개). 읽어 보면 세 종류다. ① 초안이 근거에 없는 수식어·인과를 덧붙인 진짜 지적(예: 포부 문장의 "AutoEver Code처럼 개발자를 돕는", "기능 개발 방향에 반영하겠다"), ② 근거가 잘려서 못 본 것(예: 사용자가 직접 쓴 자소서 문장인 "모바일 퍼즐 게임사"가 근거 발췌에 없어 표시), ③ 지나치게 엄격한 지적(예: 근거의 "Keycloak"을 "인증 자격증명"으로 줄인 것을 "일부 정보 누락", 헤드라인의 정체성 표현). 정확도(precision)는 라벨이 없어 재지 못했다. 이 분류는 내가 읽고 나눈 것이다.

### 확인하지 못한 것
- 같은 입력에서 판정이 달라지는 원인. temperature 0인데도 달라졌다. 모델 호출의 비결정성이라고 추정하지만 확인하지 않았다.
- 새 공고의 새 초안에서의 성능. 표본이 한 건(공고 1개)이고 개발 표본이다.
- 실행 횟수. 2번이라 평균·범위를 말할 수 없다. 최소 3번 이상 재야 한다.
- 라벨 없는 문장 표시의 정확도, LightGBM 문장이 오탐으로 나온 원인, 잘린 근거가 판정에 미친 영향(잘린 근거를 늘려서 다시 재 보지 않았다).
- 문장을 하나씩 따로 검사하거나, 여러 번 돌려 합치거나, 프롬프트를 고쳤을 때의 효과(아직 해 보지 않았다).

### 이 결과로 정한 것
- **검증기의 표시는 "확인할 문장 목록"으로만 쓴다.** 표시가 없다고 안전하다는 뜻이 아니다(특히 연결·동기를 덧붙인 문장). 보고서에도 그렇게 적혀 있다.
- 숫자를 말할 때는 "개발 표본 위에서, 같은 설정으로 2번 재서 91%와 64%"로 말한다. 한 값만 쓰지 않는다.
- 다음에 개선을 시험하면 이 표본에 맞춰 고치지 않고, **새 공고의 새 초안에서 라벨을 새로 만들어** 재고 실행을 3번 이상 반복해 범위로 적는다.
- 개선 후보(시험 전): 같은 글을 여러 번 검사해 한 번이라도 표시하면 표시(찾는 비율↑, 오탐↑), 문장을 따로 호출, 근거 발췌를 더 길게 읽기.
