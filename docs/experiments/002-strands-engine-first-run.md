## 3. qmd를 계속 띄워 두는 방법 — 문서로 확인한 것 (2026-10-04, 아직 측정 전)

**출처.** 설치된 qmd의 README(HTTP Transport 절, MCP Tool Parameters 표). 동작은 실행해서 확인하지 않았다.

- `qmd mcp --http --daemon`으로 백그라운드 서버를 띄운다(기본 `localhost:8181`, `qmd mcp stop`으로 종료). README는 이것을 "반복되는 모델 로딩을 피하는 공용 장기 실행 서버"라고 설명하고, 모델은 요청 사이에도 VRAM에 남으며 임베딩·리랭킹 컨텍스트는 5분 유휴 뒤 해제되었다가 다음 요청 때 약 1초 안에 다시 만들어진다고 적었다.
- 엔드포인트는 `POST /mcp`(MCP), `POST /query`(별칭 `/search`, MCP 없이 구조화 검색), `GET /health`. **인증이 없고** 기본으로 localhost에만 묶인다.
- `query`의 입력은 호출하는 쪽이 직접 쓴 **유형별 하위 질의**(`lex`/`vec`/`hyde`, 1~10개, 첫 번째에 2배 가중)와 `limit`, `minScore`, `rerank`(기본 true, false면 RRF만)다. 서버 안에서 질의 확장 모델을 돌리지 않는다.

**기대 효과(추정, 측정 전).** 호출마다 모델을 다시 올리는 비용(집 PC 기준 확장 없는 호출이 약 7초)이 없어지고, 질의 확장 모델도 돌 필요가 없다(우리 에이전트가 하위 질의를 직접 쓰면 된다). 호출당 13~19초가 몇 초 수준으로 내려갈 가능성이 있다.

**바뀌는 것(주의).** 이 서버가 내주는 검색은 지금 쓰는 `vsearch`가 아니라 **구조화 검색 경로**(여러 하위 질의의 RRF 결합, 조각 선택, 선택적 리랭킹)다. `vsearch`는 `[원래 질의 + 변형]` 전체에서 문서별 최고 유사도를 쓰는 방식이었다. 그래서 순위와 점수가 달라지고, 지금까지의 recall 결과(골든셋 v2 포함)가 그대로 성립한다고 볼 수 없다. 바꾸려면 HTTP 클라이언트를 `tools/`에 만들고 같은 골든셋으로 다시 채점해야 한다.

**해 볼 순서(제안).** (1) 집 PC에서 데몬을 띄워 `/query`의 응답 시간을 잰다(하위 질의 1~3개, `rerank` 켬/끔). (2) 같은 4개 질의로 `vsearch`와 `/query`의 상위 결과를 로그로 비교한다. (3) 괜찮으면 `vault_search`에 HTTP 방식을 추가하고 매핑 에이전트가 쓰게 한다.

집 PC 검색 로그(`strands-home.jsonl`)로 확인했다. 요구 3에서 에이전트는 검색을 5번 했고, 5번 모두 DevCraft 페이지가 결과에 **나왔다.** 그런데 나온 조각은 줄 6(개요), 29(후보 추가), 68(AWS 참고자료 검토), 131(추상 패턴과의 관계)이었고, 오늘 추가한 "구현 현황"(81~103줄)은 한 번도 나오지 않았다.

| 단계 | 시간 | 이 시간에 든 것 |
|---|---|---|
| (a) `qmd status` | 0.67초 | 프로세스 시작 + DB 열기(모델 안 씀) |
| (b) `query "vec: …" --no-rerank` | 7.2초 | (a) + 임베딩 모델 준비·질의 임베딩·벡터 검색 |
| (c) `vsearch` | 12.6초 | (b) + 질의 확장 모델 |
| (b) 같은 질의 반복 | 7.2초 | 질의 임베딩이 캐시되지 않음을 확인 |

- 프로세스 시작은 1초 미만이다. **임베딩 단계가 약 6.5초, 질의 확장이 약 5.4초**다.

- README는 상시 서버에서 모델이 메모리에 남아 있을 때 컨텍스트 재생성이 약 1초라고 적고 있다. 이것이 맞다면 6.5초 중 대부분이 호출마다 반복되는 로딩일 가능성이 높다. **이 6.5초를 모델 로딩, GPU 초기화, 실제 계산으로 쪼개서 재지는 않았다.**
- 질의 확장 모델은 글자를 한 토큰씩 차례로 만드는 방식이라 코어를 늘려도 단계가 병렬로 줄지 않는다(모델 로딩 시간이 같이 들어 있어 순수 생성 시간은 모른다).

## 5. qmd 상시 서버(HTTP) `/query` 시험 (2026-10-04, 집 PC)

### 시험 중 알게 된 사실
- **윈도우 OpenSSH는 접속이 끝나면 그 세션에서 띄운 프로세스를 같이 종료했다.** `qmd mcp --http --daemon`이 "시작됨(PID 34272)"이라고 출력했지만 별도 접속에서는 프로세스도 로그도 없었다. 그래서 서버 시작·측정·종료를 한 접속 안에서 하는 `scripts/run_probe_with_qmd_server.ps1`을 만들었다(자기가 띄운 PID만 종료). 오래 떠 있는 서버가 필요하면 작업 스케줄러 같은 윈도우 쪽 방법이 따로 필요하다(시도 안 함).
- **서버는 `::1:8181`(IPv6)에서만 듣는다**(스크립트가 `Get-NetTCPConnection`으로 확인). 그래서 `127.0.0.1`(IPv4)로 접속하면 닿지 않는다. 처음 시도가 "60초 안에 응답 없음"으로 실패한 원인이다. 접속 주소를 `localhost`로 바꾸자 바로 응답했다.
- PowerShell 5.1은 BOM 없는 UTF-8 스크립트를 ANSI로 읽어서 한글 메시지가 깨졌다. 스크립트를 ASCII로 다시 썼다.

### 응답 시간 (골든셋 v2의 질의 4개, `vec` 하위 질의 하나, 결과 60건 요청)

| 호출 | 시간 |
|---|---|
| 서버를 띄운 뒤 **맨 처음** 호출(모델을 올림) | 6.64초 |
| 그 뒤 새 질의 3개의 첫 호출(rerank 끔) | **0.06 ~ 0.09초** |
| 같은 질의 반복(rerank 끔) | 0.05 ~ 0.10초 (평균 0.07초) |
| rerank 켬 | 4.64 ~ 9.40초 (평균 5.88초, 첫 rerank 호출 9.40초는 리랭커 로딩이 섞였을 것으로 추정) |

- CLI `vsearch`는 새 질의 하나가 12.6초(집 PC)였다. **서버가 모델을 올려 둔 상태에서는 검색 하나가 0.07초**로 약 180배 빠르다. 같은 질의를 반복한 호출만 빠른 것이 아니라 처음 보는 질의도 0.06~0.09초였다(캐시 효과가 아님).
- 앞의 단계별 측정(고정 비용이 지배한다는 추정)이 맞았다. 호출마다 드는 약 7초는 모델을 불러오고 장치를 준비하는 비용이었고, 질의 확장 5.4초도 서버에서는 우리가 `vec` 질의를 직접 주니 필요가 없다.

### 같은 채점기로 비교한 검색 품질 (골든셋 v2, core 경험 7개, 로그 재채점)

| 방식 | 관점 | 경험 recall @5 / @10 | 원본 recall @5 / @10 |
|---|---|---|---|
| `vsearch`(기준) | 전체 | 43% / 43% | 14% / 14% |
| | 제외(현재 목록) | 57% / 71% | 43% / 43% |
| | 제외 + 가공된 서술 | 57% / 57% | 43% / 43% |
| `/query` rerank 끔 | 전체 | 43% / 43% | 14% / 14% |
| | 제외(현재 목록) | 57% / 71% | 43% / 57% |
| | 제외 + 가공된 서술 | 71% / 71% | 57% / 57% |
| `/query` rerank 켬 | 전체 | 57% / 71% | 43% / 43% |
| | 제외(현재 목록) | 57% / 71% | 43% / 57% |
| | 제외 + 가공된 서술 | 71% / 71% | 57% / 57% |

- **이 벤치마크에서 `/query`는 `vsearch`보다 나쁘지 않다.** 제외 관점에서 경험 recall은 같고, 제외 + 가공된 서술과 원본 recall에서는 한두 경험 더 걸렸다.
- 리랭킹을 켜면 제외 없이도(전체 관점) 경험이 걸린 비율이 43%에서 57~71%로 올랐다. 제외 관점에서는 차이가 없다.
- **한계.** core 경험이 7개라 경험 하나가 14%p다. 골든셋 라벨은 `vsearch` 결과를 본 뒤에 만들어 블라인드가 아니다. `/query`는 `vec` 하위 질의 하나만 줬다(hyde나 여러 질의는 시험하지 않음). 두 방식의 결과 조각 선택이 달라서 같은 페이지도 줄 번호가 다르게 나온다(예: `FINT-Data.md` 14줄과 116줄). 따라서 "같다"가 아니라 "이 시험에서는 나빠지지 않았다"로 읽는다.

### 결론과 다음
검색을 상시 서버로 바꾸면 요구 하나의 시간 구성(집 PC 5개 합계 292.6초 중 검색 222.5초)에서 검색이 거의 사라진다. 모델 응답(합 64.1초)과 에이전트 처리만 남으므로 5개를 약 1분 안팎에 끝낼 가능성이 있다(추정, 미측정). 해야 할 일: (1) `tools/vault_search`에 HTTP 방식을 추가하고 매핑 에이전트가 쓰게 한다, (2) 윈도우에서 서버를 어떻게 유지할지 정한다, (3) 서버(리눅스, GPU 없음)에서도 같은 효과인지 확인한다, (4) HTTP 결과의 발췌 형식을 Evidence로 쓸 만한지 확인한다.
→ (1)과 (4)는 완료(아래 6절). (3)은 서버에서 확인했다(응답 0.07~0.10초, 서버 프로세스 메모리 704~763MB). (2)는 서버에서는 `qmd mcp --http --daemon`으로 해결된다(리눅스에서는 접속이 끝나도 남는지는 이 시험에서 확인하지 못했다. 매번 시험 끝에 껐다).

## 7. qmd 상시 서버의 보안 메모와 결정 (2026-10-04, 결정은 보류)

**위험.** qmd 상시 서버(`qmd mcp --http`)는 **인증이 없다**(README: "the endpoints are unauthenticated"). 기본으로 localhost에만 묶여 다른 컴퓨터나 인터넷에서는 닿지 않는다(윈도우 집 PC에서는 `::1`에서만 듣는 것을 확인했고, 리눅스 서버에서 듣는 주소는 따로 확인하지 않았다). 그러나 **같은 기기에 로그인한 다른 사용자나 그 기기에서 도는 다른 프로그램**은 비밀번호 없이 vault 내용(자소서, 개인 프로필 글 포함)을 검색해 읽을 수 있다. 또 홈 폴더 권한(750)으로 막혀 있는 파일도 서버를 통하면 읽을 수 있어서, 서버가 **파일 권한을 우회하는 통로**가 된다. Origin·Host 검사는 웹 브라우저를 통한 DNS 리바인딩 공격만 막고, curl 같은 요청은 막지 않는다(README).

**이 서버의 현재 상황(2026-10-04 확인).**
- 로그인 가능한 일반 계정은 `ubuntu` 하나뿐이다. 홈 폴더 `750`, qmd 색인 파일 `644`(소유자 `ubuntu`, 홈 폴더 안).
- 그래서 지금 사람에 의한 위험은 거의 없다. 서버에 계정이 늘거나 다른 서비스·도구가 돌기 시작하면 다시 판단해야 한다. 이 서버가 상시 접속용이라는 점은 전역 설정에 적혀 있으나, 다른 사람이 접속할 수 있는지는 확인하지 못했다.
- 상시 서버는 **지금 꺼져 있다**(시험 때마다 시험이 끝나면 껐다).

**선택지.**
- **A. 필요할 때만 켜고 끄기(추천).** 실행 때 서버를 켜고 끝나면 끄는 래퍼(`scripts/with_qmd_server.sh`, 윈도우의 `with_qmd_server.ps1`과 같은 방식: 자기가 띄운 PID만 종료, 실패해도 종료). 켜는 데 2~3초(서버 측정 2.55초)가 들 뿐 검색 속도는 같고, 서버가 열려 있는 시간이 실행 중으로만 줄어든다. 색인 갱신 뒤 서버가 새 문서를 보는지 확인하지 못한 문제도 매번 새로 켜면 생기지 않는다.
- **B. 계속 켜 두기.** 지금은 계정이 하나라 위험이 작지만, 부팅 때 자동으로 켜는 설정(cron `@reboot`, systemd)과 색인 갱신 뒤 재시작 규칙이 필요하고 계정이 늘면 재판단해야 한다.

**결정: 보류.** 사용자가 "일단 기록만" 해 두기로 했다. 래퍼는 아직 만들지 않았다. 그때까지 서버에서는 필요할 때만 `qmd mcp --http --daemon`을 켜고 끝나면 `qmd mcp stop`으로 끈다.

## 11. 정정: "순환 참조"는 과장이었다 (2026-10-05)

### 무엇을 정정하나
8절("순환 참조" 항목)과 10절(요구 1·3의 플래그를 설명한 문장)에서 "시스템이 vault에 적어 둔 구현 상태·실행 결과를 시스템이 다시 근거로 인용하므로 순환 참조"라고 썼다. 사용자가 반박했고(DevCraft는 사용자의 실제 경험이고 vault 기록은 그 경험을 적은 것이며, 자소서 에이전트가 자기 프로젝트 기록에서 근거를 찾는 것은 자연스럽다), 검토 결과 **그 자체는 문제가 아니라고 판단한다.**
- 진짜 순환은 "시스템이 X라고 주장 → vault에 X를 적음 → X의 증거로 인용"처럼 진실이 외부에서 확인되지 않는 고리다. 이번 건은 구현이 실제로 있고(코드·커밋) vault 글은 그 요약이라 근거가 거짓이 아니다.
- 8절에서 "요구 3이 부분확인에서 확인으로 바뀐 것이 이 효과일 수 있다"고 쓴 것도 근거가 약하다. 그 사이 vault가 바뀌었고 구현도 실제로 진행됐으므로 둘을 가르지 못한다는 것만 사실이다.

### 실제로 남는 한계 (더 좁다)
1. **시간에 묶인 상태 기록을 영구 사실로 읽는다.** 글쓴이와 무관하다. 요구 3의 오탐은 "어제 실행에서 이 요구는 부분확인"이라는 실행 기록을 검증이 "경험에 대한 정정"으로 읽은 것이다. "단위 테스트 46개"처럼 낡는 값도 같은 종류다.
2. **평가 오염.** 일지·실험 기록에는 우리가 쓴 시험 질의가 그대로 들어 있어 그 질의로 검색하면 일지가 올라올 수 있다(2026-10-05 검색에서 `01_daily/2026-10-03.md:13`이 상위에 나옴). 골든셋 recall이 실제보다 좋게 나올 수 있다. 시험하지 않았다.
3. **검증의 독립성.** 근거 검색과 검증이 같은 vault를 보므로 vault 자체가 한쪽으로 틀리면 둘 다 같은 것을 본다. 이것도 글쓴이와 무관하다.

### 교훈: 실험마다 재료(vault)가 달라진다 (사용자 제안, 2026-10-05)
vault는 계속 고치면서 쓰는 살아 있는 자료라, 실험·기록·진행을 할 때마다 같은 질의의 재료가 바뀐다. 이번 세션에서만 요구 3의 판단 근거가 vault 갱신 전후로 달라졌고, 골든셋 v2도 새 원본 페이지를 만든 뒤 키워드를 사후 조정했다(002 이전 기록). 머신러닝에서 train/test/validation을 나누듯 **평가에 쓸 vault를 고정**했어야 했다는 지적이다.
- 실험 기록에 **vault의 커밋 해시를 적는다**(vault는 git이라 스냅샷 id가 공짜다). 지금까지의 실험 기록에는 없다. **2026-10-05 자동 기록을 구현했다**(`tools/vault_revision.py`): 커밋 해시에 더해, vault에 미커밋 변경이 늘 있어 해시만으로는 스냅샷이 아니므로 변경 내용의 지문(해시)과 변경 파일 수를 붙인다(표기 예: `bf7793d+0c53837e(8)`). 검색 로그(`vault_rev`), `run_strands_demo.py`의 실행 결과, `run_writer_demo.py`의 상태·초안 파일, 실행 보고서에 찍힌다. 같은 지문이어도 그 상태를 되살리려면 미커밋 변경이 어딘가에 남아 있어야 한다(커밋·stash). 이미 지난 실행들은 기록이 없다.
- 평가용으로는 해시 시점의 vault를 따로 체크아웃하고 별도 색인(`qmd --index`)을 만들어 고정한다. 평가 코퍼스에서 일지·실험 기록 페이지(시험 질의가 들어 있는 곳)를 빼거나 따로 둔다. `--index`가 우리 검색 경로(CLI·HTTP·MCP)에서 어떻게 쓰이는지는 확인하지 않았다.
- 지침(self-improving) 시험에서는 피드백을 받은 공고·문항과 **피드백에 쓰지 않은 공고·문항**을 나눈다(새 문항 블라인드 비교 계획과 같은 뜻).
- 반대로 실제 사용(자소서 작성)은 살아 있는 vault를 그대로 써야 한다. 평가와 실사용의 코퍼스를 구분한다.
