# 검증: 지금까지 한 것과 앞으로 할 수 있는 것 (2026-10-16, 내부용)

이 프로젝트의 세 목표(단계별 모듈화, 비종속성, 검증) 중 검증을 점검한 문서다. 레포 기록(내부 개발 가이드, 실험 001~004, 코드 docstring)과 웹·논문 조사를 합쳤다.
4절의 후보 중 무엇을 할지는 아직 정하지 않았다. 고르면 가설·기준을 실험 005에 먼저 적는다.
논문 내용은 arXiv 초록과 저자 글을 WebFetch로 열어 확인한 것만 적었다(WebFetch는 내용을 재구성해 주므로 원문 그대로가 아니고, 본문은 읽지 않았다). 논문 목록과 읽은 상태는 vault `03_study/AI 논문.md`에도 있다. **[추론]** 표시는 원문에 없는 내 판단이다.

## 1. 지금까지 한 검증 — 네 층

### ① 코드가 모델의 말을 대조한다 (결정적, 모델을 믿지 않는 층)
- **인용 대조**(`core/quote_match.py`): 모델이 "자료에 이 구절이 있다"고 하면 코드가 원문에서 직접 찾는다. 조사 단계(Brief의 출처)와 문장 검증(ClaimChecker의 인용) 둘 다 쓴다. 따옴표·각주·강조 표기 차이만 보정한다.
- **검증기 판정의 재확인**(`engines/strands/verifier.py`): 플래그 근거로 댄 ref가 실제 검색 결과에 있었는지 코드가 대조하고, 이유 칸에는 모델 문장 대신 검색 발췌를 붙인다.
- **구조 고정**(`engines/strands/claim_checker.py`): 문장 번호는 코드가 매기고, 빠진 판정은 "근거 없음"으로 채우고, 없는 번호는 버린다. 소재 계획의 대응표도 모델이 아니라 코드가 만든다.

### ② 모델이 판정한다 (LLM-as-judge 층)
- **경험 단위 검증(Verifier)**: 근거가 말하는 경험을 vault 전체에서 다시 모아 정정·모순을 찾는다. 정정이 한 곳에만 있는 문제("격리를 검증", 프로젝트A의 LangGraph 범위) 때문에 페이지가 아니라 경험 단위로 만들었다.
- **문장 단위 검증(ClaimChecker)**: 초안 문장마다 쓴 근거가 뒷받침하는지 판정한다.

### ③ 사람이 확인하는 지점 (human-in-the-loop)
- 조사 보고서 승인, 소재 계획 승인, 기본 요건 `mark`, 매핑·검증 상태의 읽는 용 문서(`state_review`).
- 검증기 표시는 "확인할 문장 목록"으로만 쓰고, 표시가 없다고 안전하다고 하지 않는다(실험 004의 결정).

### ④ 검증기를 검증한다 (메타 평가)
- 검색: 골든셋 recall, 자기 문장으로 찾기(known-item), 검색 로그 재채점(실험 001).
- 문장 검증: 사람 라벨 27개로 찾아낸 비율·오탐 측정(실험 004).
- 실험 위생: 가설을 결과 전에 적기, 표본 오염(프롬프트 예시가 표본과 겹침) 제거, `vault_rev` 기록, 프롬프트 해시 기록.
- 단위 테스트 312개(가짜 모델, AWS·qmd 호출 없음).

**잘 된 점**: ①층이 있다는 것이 이 프로젝트의 특징이다. "모델이 검증한다"에서 끝나지 않고 모델이 댄 근거를 코드가 다시 확인한다.

## 3. 조사한 연구와 우리에게 닿는 점

### 3.1 temperature 0인데 왜 달라지나 — 비결정성
- Thinking Machines, "Defeating Nondeterminism in LLM Inference"(2025): 추론 서버가 비결정적인 주된 이유는 **부하(배치 크기)가 요청마다 달라지기 때문**이라고 한다(커널이 batch-invariant하지 않음). Qwen3-235B를 temperature 0으로 1000번 돌려 **서로 다른 완성 80개**가 나왔고, batch-invariant 커널을 켜자 1000개가 모두 같았다.
  - 우리에게: Bedrock 쪽 배치를 우리가 통제할 수 없다. **[추론]** 실험 004의 변동도 이 계열일 가능성이 높지만 확인한 것은 아니다. 결론은 "고정할 수 없으니 반복해서 재고 범위로 보고한다".

### 3.2 반복 실행을 어떻게 보고하나 — pass^k, error bars
- τ-bench(Yao 외, ICLR 2025): 에이전트의 **여러 번 시도에 걸친 신뢰도**를 재는 지표 pass^k를 제안했다(k번 모두 성공할 확률). gpt-4o도 retail에서 pass^8이 25% 미만이었다.
  - 우리에게: "검증기가 이 틀린 문장을 **k번 돌려 k번 다** 잡는가"로 바로 옮길 수 있다. 실험 004의 "두 번 다 표시 7개 / 한 번만 3개 / 두 번 다 놓침 1개"가 사실상 pass^2 집계다.
- Miller, "Adding Error Bars to Evals"(2024, Anthropic): 평가는 실험이고, 질문들은 보이지 않는 모집단에서 뽑힌 표본으로 보고 분석·모델 비교·**평가 크기 계획** 공식을 제시한다.
  - 우리에게: flag 11개로는 구간이 매우 넓다. **[내 계산, Wilson 95% 구간]** 10/11 → 약 62~98%, 7/11 → 약 35~85%. 즉 두 실행의 차이도, 개선 전후의 차이도 이 표본 크기로는 구분이 어렵다. 다음 평가에서 라벨을 몇 개 만들지 먼저 계산하는 근거가 된다.

### 3.3 "결과를 본 뒤 기준을 맞추지 않는다"의 한계 — criteria drift
- Shankar 외, "Who Validates the Validators?"(UIST 2024): 사람은 출력을 채점하려면 기준이 필요하지만, **출력을 채점하면서 기준을 정의하게 된다**(criteria drift). 일부 기준은 본 출력에 의존해서, 평가를 출력 관찰과 독립으로 가정하는 방식에 의문을 던진다.
  - 우리에게: 실험 004에서 "어떤 종류의 오류를 잡을지 정한 것 자체가 이 표본에서 나왔다"고 적은 것이 정확히 이 현상이다. 피할 수 없는 일이므로 **개발 표본(기준을 만드는 곳)과 평가 표본(새 공고, 검증기 결과를 보기 전에 라벨)** 을 나누는 것이 대응이다. 이미 004의 "다음 할 일"에 있는 방향을 연구가 뒷받침한다.

### 3.4 놓치는 "연결·동기" 문장 — 쪼개서, 따로 묻기
- FActScore(Min 외, EMNLP 2023): 긴 글을 **원자 사실(atomic facts)** 로 쪼갠 뒤 각각 근거가 뒷받침하는 비율을 잰다. 한 덩어리 판정은 맞는 내용과 틀린 내용이 섞인 글을 제대로 못 본다는 문제의식.
- Chain-of-Verification(Dhuliawala 외, 2023): 초안 → 검증 질문 계획 → **질문마다 다른 답에 영향받지 않게 독립적으로 답하기** → 최종 응답. 환각이 줄었다고 보고.
  - 우리에게: "이 프로젝트로 우수상을 받았다"는 원자 사실로 쪼개면 ①우수상을 받았다(근거 있음) ②그 원인이 이 프로젝트다(근거 없음)가 된다. 지금은 문장 하나를 통째로 보니 ①에 끌려 "뒷받침됨"이 나왔다. **[추론]** 인과·동기를 별도 원자 사실로 떼어 내 따로 묻는 것이 놓친 종류에 가장 직접 닿는다. 단 문장 하나당 호출이 늘어 비용이 커진다.

### 3.5 여러 번 돌려 합치기 — 자기 일관성
- SelfCheckGPT(Manakul 외, EMNLP 2023): 모델이 아는 사실은 여러 번 샘플링해도 일관되고, 환각은 샘플끼리 갈라지고 모순된다는 점을 써서 외부 자료 없이 환각을 찾는다.
  - 우리에게: 그대로 쓰는 것은 아니다(우리는 근거가 있고, 이 논문은 글을 **쓴** 모델을 샘플링한다). **[추론]** 다만 "검증기를 k번 돌려 판정이 갈리는 문장 = 불확실한 문장"으로 보는 응용은 가능하고, 실험 004의 "한 번이라도 표시하면 표시" 후보와 같은 방향이다.

### 3.6 쓰는 모델과 검사하는 모델이 같을 때 — self-preference
- Panickssery·Bowman·Feng, "LLM Evaluators Recognize and Favor Their Own Generations"(NeurIPS 2024): 평가자 LLM이 **자기 출력에 더 높은 점수**를 주며, 자기 글을 알아보는 능력과 이 편향의 세기가 선형 상관이었다.
  - 우리에게: 이 연구는 선호 점수 평가이고 근거 대조형 사실 검증이 아니다. **같은 편향이 ClaimChecker에 있는지는 확인된 바 없다.** 그래서 오히려 실험할 가치가 있다: 검증기 모델만 바꿔 같은 표본을 잰다.

### 3.7 작고 전용인 검사기 — MiniCheck
- MiniCheck(Tang·Laban·Durrett, EMNLP 2024): (문서, 문장)을 받아 뒷받침 여부를 내는 작은 모델(최고 모델 770M)로 GPT-4 수준 정확도를 약 400배 낮은 비용으로 냈다고 보고. 벤치마크 LLM-AggreFact 공개.
  - 우리에게: `ClaimChecker` 인터페이스를 **Strands 없이** 구현하는 후보다(엔진 교체 증거와 검증 실험을 동시에). **한국어 성능은 확인하지 못했다**(학습·평가가 영어 위주로 보인다 — 이것도 원문 미확인).

### 3.8 보장까지 원하면 — conformal factuality (참고만)
- Mohri·Hashimoto(ICML 2024): conformal prediction으로 출력을 **덜 구체적으로 물러서게(back-off)** 해서 80~90% 정확성 보장을 주면서 원래 출력 대부분을 유지. 사람 라벨 소수가 필요.
  - 우리에게: 자소서는 구체성이 생명이라 "덜 구체적으로" 고치는 방식이 맞지 않고, 보정용 라벨도 지금 없다. **지금은 하지 않는 쪽을 권한다.** "검증을 어디까지 갈 수 있는가"의 상한으로만 알아 둔다.

## 4. 앞으로 할 수 있는 것 — 후보 (고르는 용)

방향 메모(2026-10-13, "기능보다 비교 실험·측정, 같은 평가로 축을 하나씩 갈아 끼우기")에 맞춰, 각 후보가 **검증**과 **비종속성 증거** 중 무엇을 같이 만드는지 표시했다. AWS 호출이 있는 것은 비용 확인 뒤에 돌린다.

| # | 후보 | 검증 | 비종속성 | 비용·코드 | 근거 |
|---|---|---|---|---|---|
| A | **새 공고로 평가 표본 만들기**: 검증기 결과를 보기 전에 사람이 라벨, 라벨 수는 구간 폭으로 미리 정함. 이후 모든 비교의 바탕 | ◎ | 바탕 | 사람 시간이 큼, 코드 거의 없음 | 3.2, 3.3 |
| B | **반복 측정 기본화**: 같은 조건 k≥3회, "k번 다 잡음/가끔/못 잡음"과 구간으로 보고 | ◎ | ○ | 호출 k배, 평가 스크립트 소폭 | 3.1, 3.2 |
| C | **검증기 모델만 교체**(Sonnet → 다른 모델): 같은 표본에서 비교 | ○ | ◎ 모델 축 | Bedrock 호출, 코드 없음(`MAS_MODEL_ID`) | 3.6 |
| D | **인과·동기를 떼어 따로 묻는 검사**(원자 사실 분해 / 문장별 독립 호출) | ◎ 놓치는 종류 겨냥 | △ | 호출 수 증가, 새 코드 중간 | 3.4 |
| E | **Strands 없는 ClaimChecker**(MiniCheck 등 또는 Bedrock 직접 호출) | ○ | ◎ 엔진 축 | 한국어 성능 미확인, 코드 중간 | 3.7 |
| F | **공통 계약 테스트**: 단계 인터페이스마다 "어느 구현이든 통과해야 하는 테스트"를 하나로 두고 가짜·Strands·새 구현이 같이 돌게. + `core/`가 프레임워크를 import하지 않음을 테스트로 강제 | △ | ◎ | AWS 없음, 코드 작음 | 일반 SW 관행(논문 아님) |
| G | 작은 정비: 근거 발췌 400자 제한 늘려 재측정, 인용 원문 저장(LightGBM 오탐 원인 확인) | ○ | – | 작음 | 실험 004 |

**내 추천 순서**: F(작고 AWS 없음, 비종속성을 "주장"에서 "테스트로 강제"로) → A+B(이후 모든 비교의 바탕) → C(코드 없이 모델 축 증거 + self-preference 확인) → D 또는 E.
A를 하기 전에 C·D·E를 재면 지금의 개발 표본 위 숫자가 또 나올 뿐이라 비교의 의미가 약하다.
